# Encryption at Rest — Control Evidence (SOC2)

**Control:** Customer data stored in object storage is encrypted at rest.
**Scope:** All GLerp tenant MinIO object stores (per-tenant file storage for ERPNext/Frappe
attachments via `dfp_external_storage`), across the production RKE2 cluster.
**Status:** In effect and standard architecture. Deployed by the `glerp` Helm chart
(`tenant.minio.kes.enabled: true`, default) and verified per site.

---

## 1. Control statement

All customer files stored in GLerp's object storage are encrypted at rest using **server-side
encryption with a Key Management Service (SSE-KMS)**. Encryption keys are managed by **MinIO KES
(Key Encryption Service)** with **HashiCorp Vault** as the key store. Each tenant has a **distinct
encryption key**. The KMS root key is never persisted in a Kubernetes Secret or on a MinIO node in
plaintext — it is held in Vault and released only to the tenant's KES service over an
authenticated, mutually-TLS'd channel.

## 2. Architecture

| Layer | Implementation |
|---|---|
| Cipher / mode | AES-256 GCM, SSE-KMS (MinIO server-side encryption, KMS-managed keys) |
| Key service | MinIO **KES** sidecar (image `minio/kes`), one per tenant MinIO deployment |
| Key store | **HashiCorp Vault** (KV v2 secrets engine), authoritative store for the KMS root key |
| KES → Vault auth | Kubernetes ServiceAccount JWT (Vault Kubernetes auth), over service-mesh mTLS |
| Key per tenant | `<namespace>-minio-key`, stored at Vault path `secret/<namespace>/minio-kes/root-key/…` |
| Data path | Objects encrypted by MinIO on write using data keys wrapped by the KES/Vault root key |

**Key custody:** The root key is generated and stored inside Vault by KES on first use. It is
**not** written to any Kubernetes Secret, container image, or MinIO volume. Data-encryption keys
are per-object, generated by KES on demand and never stored in plaintext at rest.

**Separation of duties:** Storage operators (MinIO) do not hold the KMS root key; key custody is
in Vault, which is separately administered.

## 3. Enforcement (how it is applied, not just available)

- The encryption architecture is **templated into the GLerp Helm chart** and enabled **by
  default** for every tenant (`tenant.minio.kes.enabled: true`). A tenant cannot be deployed in
  the standard configuration without it.
- On every install/upgrade, an automated Kubernetes Job configures the KES↔MinIO trust, ensures
  the tenant's KMS key exists, and sets the bucket's default encryption to `sse-kms`. This makes
  **every new object write encrypted** without operator action.
- Bucket-level default encryption (`mc encrypt set sse-kms`) means writes that omit an explicit
  encryption header are still encrypted by the server.

## 4. Verification / evidence (reproducible)

Run against any tenant's MinIO (from a MinIO pod, container `minio`; credentials from the
`<namespace>-minio-creds` Kubernetes Secret):

```
$ mc admin kms key status <alias>
Key: <namespace>-minio-key
   - Encryption ✔
   - Decryption ✔

$ mc encrypt info <alias>/<namespace>
Auto encryption 'sse-kms' is enabled with KeyID: <namespace>-minio-key

$ mc stat <alias>/<namespace>/<an-object-written-after-enablement>
...
Encryption: SSE-KMS (arn:aws:kms:<namespace>-minio-key)
```

- `Encryption ✔ / Decryption ✔` proves the full MinIO → KES → Vault key path is operational.
- The `Encryption: SSE-KMS` line on a stored object proves data at rest is encrypted with the
  KMS-managed key.

## 5. Scope boundaries and compensating design

- **In scope (encrypted at rest):** customer files in MinIO object storage.
- **Encryption in transit inside the cluster is intentionally not applied to the internal S3
  data path** (`requestAutoCert: false`): the RKE2 cluster is a single trusted physical location,
  the TLS trust boundary to end users is owned by the Traefik ingress, and the one leg that
  crosses a trust boundary — KES retrieving the root key from Vault — **is** mutually TLS'd over
  the service mesh. This is a deliberate, documented design decision, not an omission.
- **Not retroactive:** SSE-KMS encrypts objects written after enablement. Objects that predate a
  site's enablement are re-encrypted in place via a scheduled backfill (`mc cp --recursive`),
  tracked per site.

## 6. Key isolation model (current state — disclosed)

Each tenant uses a **distinct key** at a **distinct Vault path** (`secret/<namespace>/…`). The
Vault **authentication role** used by KES is shared across tenants (`glerp-minio-kes`); its policy
scopes each request to the caller's own namespace path segment. A residual property — a KES
service in one namespace could, using its own credential, reach another namespace's key path — is
**documented and accepted**. The stricter per-tenant-role isolation requires Vault Enterprise
templated ACLs (not licensed here) or a per-tenant provisioning step; it is planned as a future
hardening and does not affect the "encrypted at rest" control, which is fully met. See
`chart/glerp/TENANT.md` → "Key scoping across namespaces."
