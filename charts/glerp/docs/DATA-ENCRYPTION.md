# Data Encryption — Control Evidence (SOC2)

**Control:** Customer data is encrypted at rest across all persistent data stores.
**Scope:** Every GLerp tenant on the production RKE2 cluster — object storage (customer file
attachments), the application database (MariaDB), and the shared site-assets volume.
**Status:** In effect and standard architecture. Enforced by the `glerp` Helm chart plus
cluster-level encrypted storage, and verified per site (see the attestation table in §6).

> This document is the auditor-facing control summary. Engineering/architecture detail and the
> operational runbook live in [`ENCRYPTION-ARCHITECTURE.md`](ENCRYPTION-ARCHITECTURE.md) and
> [`../TENANT.md`](../TENANT.md).

---

## 1. Control statement

All customer data persisted by a GLerp tenant is encrypted at rest, across every storage layer:

- **Object storage (customer files)** — encrypted with **server-side encryption using a Key
  Management Service (SSE-KMS)**, AES-256-GCM, keys managed by **MinIO KES** with **HashiCorp
  Vault** as the key store. Each tenant has a **distinct** encryption key. The KMS root key is
  never persisted in a Kubernetes Secret or on a MinIO node in plaintext.
- **Application database (MariaDB)** and the **shared site-assets volume** — stored on
  **Longhorn LUKS/dm-crypt encrypted volumes**. Data is encrypted by the CSI driver before it
  touches disk; the LUKS passphrase is held in a cluster-administrator-managed Secret, separate
  from the data.

## 2. Coverage — every persistent data store

| Data | Where it lives | At-rest mechanism | Cipher | Key custody |
|---|---|---|---|---|
| Customer files (Frappe attachments via `dfp_external_storage`) | MinIO object store (DirectPV drives) | **SSE-KMS** via MinIO KES + Vault | AES-256-GCM | Per-tenant key in Vault; root key never in a K8s Secret |
| Application database | MariaDB PVC `data-glerp-mariadb-sts-0`, StorageClass `longhorn-crypto-mariadb-rwo` | **Longhorn LUKS / dm-crypt** volume | AES (LUKS/`ext4`) | LUKS passphrase in the `longhorn-crypto` Secret (`longhorn-system`) |
| Shared site assets | RWX PVC `glerp`, StorageClass `longhorn-crypto-rwm` | **Longhorn LUKS / dm-crypt** volume | AES (LUKS/`ext4`) | Same `longhorn-crypto` Secret |

There is no GLerp persistent data plane that is unencrypted at rest.

## 3. Key custody & separation of duties

- **MinIO SSE-KMS root key** — generated and stored **inside Vault** by KES on first use; never
  written to any Kubernetes Secret, container image, or MinIO volume. Per-object data-encryption
  keys are generated by KES on demand and never stored in plaintext. Storage operators (MinIO) do
  **not** hold the root key — custody is in Vault, which is separately administered. Each tenant's
  key is at a distinct Vault path (`secret/<namespace>/minio-kes/root-key/…`).
- **Longhorn LUKS passphrase** — held in a single cluster-level Secret `longhorn-crypto` in the
  `longhorn-system` namespace (key `CRYPTO_KEY_VALUE`), applied once by a platform administrator as
  cluster infrastructure. It is **not** stored in the chart or in git, and is outside any tenant
  namespace. The CSI driver references it via the encrypted StorageClasses' node-stage/publish
  secret parameters; it is used only to unlock volumes at mount time.
- **Tenant credentials** (MinIO access/secret keys, MariaDB root password) are a **separate**
  concern from the encryption keys above: they are generated per tenant and stored in Vault, synced
  into the namespace by External Secrets Operator. They do not grant access to the at-rest
  encryption keys.

## 4. Enforcement (how it is applied, not merely available)

- **Object storage:** SSE-KMS is **templated into the GLerp Helm chart** and enabled **by default**
  for every tenant (`tenant.minio.kes.enabled: true`). On every install and upgrade, an automated
  Kubernetes Job establishes the MinIO↔KES trust, ensures the tenant's KMS key exists, and sets the
  bucket's **default** encryption to `sse-kms` — so every new object write is encrypted with no
  operator action. A tenant cannot be deployed in the standard configuration without it.
- **Database & assets:** the chart provisions the MariaDB and shared-asset volumes **exclusively on
  the encrypted (`longhorn-crypto-*`) StorageClasses**. A volume cannot be created for these
  workloads on unencrypted storage in the standard configuration.

## 5. Verification / evidence (reproducible)

### 5a. Object storage (MinIO SSE-KMS)

From a MinIO pod (container `minio`; credentials from the `<namespace>-minio-creds` Secret):

```
$ mc admin kms key status <alias>
Key: <namespace>-minio-key
   - Encryption ✔
   - Decryption ✔

$ mc encrypt info <alias>/<namespace>
Auto encryption 'sse-kms' is enabled with KeyID: <namespace>-minio-key

$ mc stat <alias>/<namespace>/<an-object-written-after-enablement>
...
Encryption: SSE-KMS (arn:aws:kms:<namespace>-minio-key)
```

- `Encryption ✔ / Decryption ✔` proves the full MinIO → KES → Vault key path is operational.
- The `Encryption: SSE-KMS` line on a stored object proves the object at rest is encrypted with the
  KMS-managed key.

### 5b. Database & assets (Longhorn LUKS)

```
# The StorageClass declares encryption:
$ kubectl get sc longhorn-crypto-mariadb-rwo -o jsonpath='{.parameters.encrypted}'
true

# The workload's PVC is bound on that encrypted class:
$ kubectl -n <namespace> get pvc data-glerp-mariadb-sts-0 \
    -o jsonpath='{.spec.storageClassName}'
longhorn-crypto-mariadb-rwo

# The underlying Longhorn volume reports encrypted=true:
$ kubectl -n longhorn-system get volumes.longhorn.io <pv-name> \
    -o jsonpath='{.spec.encrypted}'
true
```

- A PVC bound on a `longhorn-crypto-*` class (`encrypted: true`) proves the data is written to a
  LUKS/dm-crypt device; the raw block device is ciphertext without the `longhorn-crypto` passphrase.

## 7. Scope boundaries and compensating design

- **In scope (encrypted at rest):** customer files (MinIO), the application database (MariaDB), and
  shared site assets — i.e. every GLerp persistent data plane.
- **In-transit inside the cluster** is intentionally *not* applied to the internal S3 data path
  (MinIO runs with `requestAutoCert: false`, plain HTTP on `:80`): the RKE2 cluster is a single
  trusted physical location, the TLS trust boundary to end users is owned by the Traefik ingress,
  and the one leg that crosses a trust boundary — KES retrieving the root key from Vault — **is**
  mutually TLS'd over the service mesh. This is a deliberate, documented decision, not an omission.
- **Not retroactive (MinIO):** SSE-KMS encrypts objects written after enablement. Objects that
  predate a site's enablement are re-encrypted in place via a scheduled backfill
  (`mc cp --recursive`), tracked per site.
- **Key-isolation residual (MinIO):** each tenant uses a distinct key at a distinct Vault path, but
  the Vault **auth role** (`glerp-minio-kes`) is shared across tenants; its policy scopes each
  request to the caller's own namespace path segment. A KES service could, using its own credential,
  reach another namespace's key path. This is **documented and accepted**; stricter per-tenant-role
  isolation requires Vault Enterprise templated ACLs (not licensed) or a per-tenant provisioning
  step. It does not affect the "encrypted at rest" control, which is fully met.
